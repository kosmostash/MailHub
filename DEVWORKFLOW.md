# Development workflow, and notes on building MailHub with KosmoJS

This document is for people who will work on MailHub or who are weighing KosmoJS for a
project of their own. It has three parts: how to work in this repository day to day, what
building the whole application on KosmoJS 0.4.4 was actually like, and a comparison of the
key implementation decisions with how the same things would be done on Next.js, TanStack
Start and SvelteKit.

I am the AI assistant that wrote MailHub from the functional specification, end to end,
over one session. The impressions below are mine; they are specific and dated (KosmoJS
0.4.4, September 2026) and some of the rough edges will have moved by the time you read
this. Where a problem turned out not to be KosmoJS's, I say so.

---

## 1. Working in this repository

### Layout

```
src/api/        submission API           Hono    base "/api", apiBase "/"   private (LAN)
src/webhooks/   delivery-event webhooks  Hono    base "/webhooks", apiBase "/"   public
src/admin/      web application          Solid + H3   base "/admin", apiBase "/api"   public
src/docs/       documentation            MDX (SSR)    base "/"                 public
domain/         business logic, framework-free; imported as @/domain/...
workers/        sender and SMTP listener: plain Node processes, not KosmoJS folders
db/             knex migrations and the migration runner
test/           vitest suites, the §8 conformance run, the Chromium e2e script
lib/            generated by kosmo; only types.ts and cache.json files are committed
```

Each `src/<folder>` is a KosmoJS *source folder*: its own `kosmo.config.ts`, its own
backend and frontend generators, its own `api/` and `pages/` trees. `kosmo build` emits one
`dist/run.js` that serves all four on one port, routing by longest prefix with API prefixes
ahead of page prefixes. The public/private split the specification asks for is done at the
reverse proxy by path (see `deploy/Caddyfile`), not in code.

### Commands

| Command | What it does |
| --- | --- |
| `pnpm dev` | KosmoJS dev server for every folder on :4556 (admin app at `/admin`) |
| `pnpm sender`, `pnpm smtp` | the two worker processes, via tsx |
| `pnpm build [folder]` | `kosmo build` for all folders or one, then tsdown for the workers (`scripts/build.mjs`) |
| `pnpm typecheck [folder]` | per-folder `tsc` with the generated path mappings; needs a build or dev run first |
| `pnpm migrate [latest\|rollback\|status\|make <name>]` | knex migrations, TypeScript, through tsx |
| `pnpm test` | vitest against `TEST_DATABASE_URL`; includes `test/conformance.test.ts` |
| `pnpm e2e` | Chromium walkthrough of the admin app against a fresh database |

Tests need a real Postgres. Nothing is mocked at the database layer, on purpose: the partial
unique index that guarantees a single superadmin, `SKIP LOCKED` in the sender, cascade and
restrict rules on foreign keys are the product, and mocks would hide them.

### The shape of a change

1. **Domain first.** Write the behaviour in `domain/` as plain functions taking an `Actor`
   (the acting identity plus the impersonator, if any) and throwing `DomainError` with the
   status code the specification names. Add a domain test.
2. **Route second.** Add `api/<name>/index.ts` in the right folder. Request and response
   types go in the handler's type parameter; KosmoJS turns them into TypeBox validators and
   into the typed fetch client. Keep handlers thin: unpack, call the domain, return.
3. **UI third.** Pages import `fetchClients` from `_/fetch` and never build URLs. Queries
   go through TanStack Solid Query with the query key naming the resource.
4. **Build, typecheck, test.** `pnpm build admin && pnpm typecheck admin` after adding or
   removing a route: the generated `lib/` is what the typecheck sees. Deleting a route
   leaves its generated files behind; remove `lib/<folder>/api/<route>` by hand or the
   typecheck fails on a stale file.
5. Extend `test/conformance.test.ts` or `test/e2e/walkthrough.mjs` when the change touches
   a step of the specification's §8 walk-through.

### Conventions that matter

- **Scoping is in the query, never after it.** Repositories take a `Scope` and add the
  `WHERE`; out-of-scope ids look exactly like missing ones (404).
- **Every write records activity inside the same transaction**, with actor snapshots, so
  a deleted account keeps its history.
- **Side effects that must survive a thrown error go outside the transaction.** The
  wrong-code counter in `domain/confirmation` is the worked example.
- **Errors are one shape everywhere**: `{ error: { code, message, details? } }`, from all
  three backends.
- **Secrets never leave the process.** Provider configs are encrypted at rest and masked
  in every response; the mask sent back on update means "keep".

## 2. Impressions of KosmoJS

### What surprised me, positively

**Validation and the fetch client fall out of the route's TypeScript types.** Writing
`POST<{ json: { email: VRefine<string, { format: "email" }> }, response: [201, "json", User] }>`
produced, without any further declaration, a TypeBox validator that rejects bad payloads
with per-field detail, a client function `api["admins"].POST([], { json })` whose argument
and return types match the handler, and client-side validation before the request goes
out. In every other stack this is three artefacts kept in sync by discipline (a schema, a
handler type, a client type) or by a heavier layer such as tRPC or an OpenAPI generator.
Here it is one. Over roughly forty routes I never once had a client and server disagree
about a shape, and route changes surfaced as type errors in the pages that used them.

**One project, several apps, each with its own backend.** The submission API and the
webhooks run on Hono; the admin API runs on H3; the docs are MDX with server rendering. All
of that is one `pnpm dev`, one build, one `dist/run.js`, and the folder boundaries are the
deployment boundaries. Splitting the private submission surface from the public admin app
was a configuration decision, not an architecture project.

**The build is fast and the output is plain.** A full build of four folders plus the
worker bundle takes a few seconds. `dist/run.js` is readable Node code on `node:http`, with
no framework runtime to deploy, and it also runs on Bun and Deno untouched. The dev server
logs the prefix table it will route by, which is exactly the thing you want to see.

**Cascading middleware with slots** is a small idea that paid off repeatedly. The admin
folder's global `use.ts` requires a session and puts the auth context on the event; the
three public routes (bootstrap, sign-in, sign-out) replace that middleware at the `auth`
slot with a pass-through. The submission folder does the same with a `collection` slot and
a health route. No route lists, no path regexes, no "except" arrays.

**Type-safe navigation.** The generated `Link` component takes `["collections/[id]", id]`
and refuses unknown routes or missing parameters at compile time.

### What confused me

**Base and apiBase composition.** A folder at `base: "/api"` gets API routes at
`/api/api/...` unless `apiBase` is set to `"/"`; a folder at `base: "/"` with the default
`apiBase` gets `/api/...`. Both are consistent once you know that the API prefix is
`join(base, apiBase)`, but the first build with two folders put routes where I did not
expect them and I only understood it by reading the generated `dist/run.js`. A one-line
table in the config docs would have saved that hour. Related: with `apiBase: "/"`, the
bare prefix `/api` answers 404 while `/api/emails` works, which is correct and still
looked like a bug at first.

**Context typing differs per backend, and I misread it at first.** A Hono folder's
`env.d.ts` declares `DefaultVariables` and `DefaultBindings` (set with `ctx.set()`); an H3
folder's declares `DefaultContext` (values assigned on `event.context`). The scaffold gets
this right for each backend; I checked by generating a fresh folder of each kind. An
earlier version of this document claimed the H3 scaffold carried the Hono names. It does
not; that impression came from a Hono folder I had scaffolded first and then replaced
with H3. The lesson for readers is only that the names are backend-specific, and that the
generated `lib/<folder>/api.ts` is where to confirm which one applies.

**The type resolver follows direct imports only.** A response type re-exported through
`export type { X } from "./registry"` came out of the generator as a bare name and broke
the typecheck; importing it from the defining module fixed it. Nothing warns.

**A root `pages/layout.tsx` is not applied** (in the Solid generator at least). Layouts
work in subdirectories; the whole-app wrapper is `app.tsx`. The docs show subdirectory
layouts, so this is more a gap in what I assumed than in what is promised.

**Response validation runs in dev and not in production builds** unless
`runtimeValidation: true` is set per route. Sensible as a default, but it means the two
environments disagree about whether a handler returning the wrong shape is an error. I
would have liked one flag at the folder level.

### What annoyed me

**Stale generated files after deleting a route.** `lib/<folder>/api/<route>/` is created
when a route appears and never removed when it disappears; the leftover `fetch.ts` then
fails the typecheck with a message about a route that no longer exists. Twice I had to
`rm -rf` a directory in `lib/` and re-run. A prune step in `kosmo build` would fix it.

**`pnpm build admin` sent the folder name to the wrong command.** That is pnpm's
argument forwarding, not KosmoJS's, but because the natural build script is
`kosmo build && tsdown`, the framework's per-folder build only works from a wrapper
script. Worth a note in the docs.

**Version skew between packages.** `@kosmojs/core` and `@kosmojs/cli` are 0.4.4; every
generator is 0.2.1; the READMEs of core, cli and dev still say "TODO: Add package
description". It all works together, but it does not look like it will until you try.

**The docs site was unreachable from my build environment** (network policy on my side),
so I read the framework through an LLM documentation index and through the generated
code. That worked, and I mention it because the generated `lib/` was good enough to learn
from: it is readable, commented, and it is the truth.

**Small things.** `VRefine` is a global type with no import, which is convenient in route
files and surprising in an editor without the folder's tsconfig loaded. The TanStack Query
option is spelled `--tsq` on the CLI and `{ tanstack: { query: true } }` in the config.
The MDX generator pulls in Preact for SSR, which is a second UI runtime in a Solid project;
harmless, but unexpected in `package.json`.

### Things that were not KosmoJS's fault, recorded so you do not blame it either

- Solid's "stale read from `<Show>`" when a child derives props from the Show accessor
  during disposal. Use `keyed` Shows for edit forms.
- UnoCSS only emitting classes it can see literally in source. Map variants to literal
  strings or safelist them.
- H3 wrapping thrown errors in its own `HTTPError`; unwrap `cause` in the error handler.
- Playwright's `getByLabel` matching a wrapping `<label>`'s full text, options included.
  Give selects `id`/`for` pairs.

### Verdict

For a multi-surface application with a real API contract, KosmoJS did the two things I
most want a full-stack framework to do: it kept the client and the server from drifting,
and it let me put the right backend on each surface without a monorepo. The price is a
young ecosystem, generated code you must commit and occasionally prune, and a few places
where the truth is in `lib/` rather than in the documentation. I would use it again for
this kind of project. I would not yet hand it to a team that expects the framework to
have an answer on Stack Overflow.

## 3. Key implementation details, compared

Each row says how MailHub does it on KosmoJS, then how I would do the same thing on
Next.js (App Router), TanStack Start, and SvelteKit, then names other options. "Same"
means the design carries over unchanged; only the mechanics differ.

### Four surfaces with different exposure on one deployment

- **KosmoJS:** four source folders with their own `base`; one `dist/run.js` dispatches by
  prefix; the proxy decides what is public. The submission API and webhooks are Hono, the
  admin API is H3, the docs are MDX SSR, all in one build.
- **Next.js:** one app; route groups under `app/api/`, `app/webhooks/`, `app/admin/`;
  everything is React and one Node runtime. Exposure is still the proxy's job; splitting
  runtimes (a Hono API next to the app) means a second package.
- **TanStack Start:** file routes under `app/routes/`, server routes for the APIs,
  Vite-based like KosmoJS; one framework, one runtime, React or Solid.
- **SvelteKit:** `src/routes/api/...`, `src/routes/webhooks/...`, `+server.ts` endpoints,
  one adapter; the same single-runtime story.
- **Others:** Nuxt (Nitro/H3 under the hood, so the H3 code here ports almost verbatim),
  SolidStart, Remix/React Router 7, Astro with server islands for the docs plus a separate
  API, or a pnpm monorepo with Hono and a SPA.

### Request validation and the typed client

- **KosmoJS:** types on the handler → TypeBox schemas → validated `ctx.validated.json`
  and a generated client; one source of truth, validation on both ends.
- **Next.js:** Zod schemas in route handlers or server actions; the client type is the
  inferred schema type, wired by hand or through tRPC, oRPC or Hono RPC mounted in a
  catch-all route. Server actions give typed calls but not a REST contract for external
  clients like MailHub's submission API.
- **TanStack Start:** server functions with `validator()` (Zod or Valibot) give the same
  typed call for internal use; external endpoints are plain server routes with manual
  validation.
- **SvelteKit:** `+server.ts` handlers with Zod; form actions for the UI; `sveltekit-superforms`
  for validated forms. No generated client for endpoints.
- **Others:** tRPC, oRPC, Hono RPC and Elysia's Eden give the typed client; OpenAPI plus
  a generator (`openapi-typescript`, Orval) gives it for any server.

### Middleware and per-route overrides

- **KosmoJS:** `use.ts` cascades down the directory; named slots let one route replace one
  middleware. The auth check and the collection-id check are two such slots.
- **Next.js:** a single edge `middleware.ts` matched by path patterns, plus per-handler
  checks; no cascade by directory.
- **TanStack Start:** route middleware and server-function middleware compose explicitly;
  closer to KosmoJS in spirit, declared in code rather than by file position.
- **SvelteKit:** `hooks.server.ts` `handle` runs for everything; per-route logic in
  `+layout.server.ts` load functions and the handlers themselves.
- **Others:** Hono and H3 directly (route groups with `app.use`), Nuxt server middleware
  (also H3), Express-style stacks.

### Sessions, impersonation and role scoping

- **KosmoJS:** cookie with an opaque token, session row (hashed id, impersonated user id,
  revoked_at), the auth middleware puts `principal`/`actor` on the context; every domain
  function takes the actor. Nothing framework-specific except reading the cookie.
- **All three:** the same design ports unchanged. Next.js reads cookies with
  `cookies()`, SvelteKit in `handle` with `event.cookies`, TanStack Start with
  `getCookie` from H3-style utilities. Auth.js, Lucia-style hand-rolled sessions, or
  Better Auth would cover sign-in; impersonation as a session attribute is still yours to
  write everywhere.

### Background sender and SMTP listener as separate processes

- **KosmoJS:** plain Node entrypoints under `workers/`, importing the domain layer through
  the `@/` alias, bundled by tsdown; KosmoJS is not involved at all, which is the point.
- **Next.js:** the same, but the domain code has to live outside the `app/` tree and be
  importable without Next's runtime; teams often reach for a queue (BullMQ) or a cron
  route hit by an external scheduler because "a long-running process next to Next" is not
  the platform's default shape, especially on serverless hosts.
- **TanStack Start / SvelteKit:** same as KosmoJS; a Vite project with a shared `lib/`
  and separate `node` entrypoints is natural.
- **Others:** a queue (BullMQ, pg-boss, Graphile Worker) if you want retries and
  scheduling managed for you; MailHub uses the database as the queue with a lease column
  and `SKIP LOCKED`, which is enough for its volumes and needs no broker.

### Error contract

- **KosmoJS:** one `errors.ts` per folder maps `DomainError`, validation errors and the
  backend's own errors to `{ error: { code, message, details } }`. H3 wraps thrown errors;
  Hono does not; the code accounts for both.
- **Next.js:** each route handler catches and returns `NextResponse.json`; no central
  handler for route handlers, so a shared helper is the usual answer.
- **TanStack Start:** server functions throw and the client receives a typed error; for
  server routes, manual.
- **SvelteKit:** `handleError` in hooks for unexpected errors, `error()`/`json()` in
  handlers; consistent enough.

### Server-side data for pages

- **KosmoJS (as used here):** client-rendered Solid pages calling the typed client through
  TanStack Query. No loaders, no SSR for the admin app, on purpose: it is authenticated
  and gains nothing from it. KosmoJS does offer loaders and SSR per folder.
- **Next.js:** server components fetch directly; mutations via server actions; caching
  semantics to learn.
- **TanStack Start:** route loaders with TanStack Query integrated, SSR by default;
  the closest analogue to what a "full" KosmoJS page would look like.
- **SvelteKit:** `load` functions and form actions; SSR by default; the most cohesive
  story of the three for form-heavy admin UIs.

### HTML preview of untrusted email content

- **Everywhere the same:** a sandboxed `<iframe srcdoc>` with an empty `sandbox`
  attribute and `referrerpolicy="no-referrer"`. No framework helps or hinders.

### Testing strategy

- **KosmoJS:** black-box HTTP tests against the built `dist/run.js` (spawned per suite),
  domain tests against a real Postgres, a conformance suite that also spawns the sender
  worker, and a Playwright script. In-process testing of the KosmoJS app is possible but
  the generated modules use Vite virtual modules, so the built server was the simpler
  target.
- **Next.js:** in-process route handler tests are awkward for the same reason (the
  runtime); most teams test against `next start` or use Playwright.
- **TanStack Start / SvelteKit:** server functions and `+server.ts` handlers are plain
  functions and unit-test well; Playwright for the rest.

### Documentation site

- **KosmoJS:** an MDX folder with SSR, a layout in `app.mdx`, typed links, at the root
  path. Nothing to install.
- **Next.js:** `@next/mdx` or Fumadocs/Nextra; **SvelteKit:** mdsvex; **TanStack Start:**
  MDX via Vite plugins. **Others:** Astro Starlight, VitePress, Docusaurus as a separate
  site.

### Styling and icons

- **KosmoJS:** `kosmo.config.ts` is a Vite config, so `plugins: [UnoCSS()]` in the admin
  folder and `import "virtual:uno.css"` in the client entry; icons as
  `i-tabler-*` classes from `@iconify-json/tabler`.
- **All three:** Tailwind or UnoCSS through their Vite or PostCSS integration; identical
  outcome. Next.js needs the PostCSS route rather than a Vite plugin.

## 4. If you continue from here

- `test/conformance.test.ts` is the definition of done; keep it green.
- The open items: build the Docker image somewhere with a daemon, a dark-theme pass over
  the admin app, a release tag.
- For a hosted provider type, add a module to `domain/providers/registry.ts` with
  `validate` and `send`, and give `src/webhooks/api/[provider]` a native-payload branch
  with raw-body signature verification. The normalized route stays as the fallback.
